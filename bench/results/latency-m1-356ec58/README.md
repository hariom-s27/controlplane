# Latency evidence pack: commit 356ec58 vs 880d5c9 (P04c, 13 Nov 2026)

## Claim

On one Windows laptop in the Best performance power mode (phase E1), the gate's
p99 per-call service time for the C1 workload was a median of **4.65 ms** over 3 runs
at commit `356ec58` (run values 3.94, 4.65, 5.27 ms), against **17.59 ms** at `880d5c9`
(17.28, 17.59, 18.96 ms). This is sequential per-call service time in one process
(concurrency 1), not response time under load. It is repeatable on one machine, not
independently reproduced.

## What was measured

- Workload: `bench/latency.py` configuration `C1_hhem_off_seq`, driven by `harness/c1_driver_p04c.py`
  in `plain` mode: the 150-case gold set cycled 7 times, n = 1,050 timed calls after 50 warm-up
  calls (discarded), concurrency 1, grounding (HHEM) off.
- Each timed call is one `controlplane.intercept._run_gate()` call: classify, resolve (live reads of
  the local SQLite stores), predicate, decide, and a signed, persisted receipt.
- LLM extraction is excluded: extraction is stubbed to the pre-built action per case, as in
  `bench/latency.py`. The downstream business tool is never called.
- The number is per-call service time, measured one call after another in one process. It is
  not response time under load.
- The protocol was written before the first run: `PROTOCOL_E.md` (with Amendment 1, the E1/E2 split).

## How to check

(a) Recompute the medians (any OS with Python 3, stdlib only, takes seconds). From this directory:

    sha256sum -c SHA256SUMS
    python summarise.py --check

`--check` rebuilds `summary.json` and `summary.md` from `runs/` and exits 1 if either differs,
if a counted run file is missing, or if any run's mix is not 378 / 602 / 70.

(b) Re-run (Windows only, because of the power-overlay and gate checks).
1. Make archive copies of 880d5c9 and 356ec58, plus the DBs from `python data/build_db.py`.
2. Edit the absolute paths in `harness/run_e.sh` (`W`, gate path), `harness/env.sh` (`PY`, `TMP`)
   and `harness/c1_driver_p04c.py` (`LAB`).
3. Run `bash run_e.sh E1 <overlay GUID>`.
The machine gate rules are fixed: never lower the thresholds. One phase (6 runs) took about
2 minutes on the machine above (file timestamps).

(c) What to expect: the times will differ by machine and power mode. The mix must be
ALLOW 378 / BLOCK 602 / ESCALATE 70 exactly.

## Limits

- One machine; 3 runs per condition. No statistical test was made, and 3 runs are too few for an interval.
- Repeatable on one machine, not independently reproduced.
- The power-mode and gate checks are Windows-specific.
- Service time with concurrency 1 only. It says nothing about response time under concurrent load.
