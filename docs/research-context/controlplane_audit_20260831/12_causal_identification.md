For each comparison: **what causal variable is actually changed?**

| Dimension | Changed? |

## K.2 Exp 5: across gold classes

Not a causal comparison at all — a partition of input space by the very features `decide()` branches on. **Classification: NOT A CAUSAL DESIGN.**

## K.3 Gate ON vs gate OFF — the negative control

**This is the repository's only genuine causal contrast**, and it is a good one.

| Dimension | Changed between arms? |
|---|---|
| agent, prompt, retrieval, model, seed, clock | **NO** — identical; `dispatch_tool` branches on `session.gate_enabled` alone |
| evidence source | **YES** — gate ON adds resolver reads at decision time |
| independence | **YES** for the policy path |
| freshness | **YES** — decision-time read vs. the agent's retrieval-time context |
| tool access | NO |

**Classification: IDENTIFIED, n=1.** The design is clean: one binary manipulation at one code branch, everything upstream held fixed.

Two threats to that identification, both real:
1. **n=1 scenario, replayed from a fixture.** The estimand is "does the gate change *this* decision", not "how often".
2. **The stale index is gitignored.** `data/stale_index/chunks.json` is generated by `data/build_db.py`, so the treatment's *cause* is not a committed artifact.

## K.4 The independence claim itself — the most important row in this file

README: *"check the claims inside it against the enterprise's own live systems of record"*; `registry/base.py`: *"Two independent reads of the same store is the liveness that matters here."*

**The base.py wording is the accurate one and it is more modest than the README's.** Decomposed by path:

| Path | Agent reads | Verifier reads | Actually independent? |
|---|---|---|---|
| **Policy / clause** | `data/stale_index/chunks.json` — a keyword index over chunked clause text, **unfiltered by `effective_to`** (`agents/servicing_agent.py::_retrieve_policy`) | `data/policy_store.db`, `WHERE effective_to IS NULL` (`registry/policy.py`) | **YES.** Different artifact, different query, different result. This is a real source-independence contrast |
| **Orders** | `data/orders.db` **directly**, via `agents/servicing_agent.py::_recent_orders` | `data/orders.db` (`registry/orders.py`) | **NO.** Same file, same table. The independence is *temporal/procedural* — a fresh read at decision time versus what the model retained in context — not source independence |
| **Entitlements** | `data/entitlements.db` directly (`agents/knowledge_assistant.py::_retrieve_documents`) | `data/entitlements.db` | **NO.** Same file. The contrast is that retrieval does not filter by entitlement while the resolver does — a **query-scope** difference, not a source difference |

**Two mechanisms are being conflated under one word:**
- **(a) Source independence** — the verifier consults an artifact the agent never saw. True only for the policy path.
- **(b) Re-derivation** — the verifier recomputes the fact from the record instead of trusting the agent's paraphrase of it. True everywhere, and it is what actually catches the orders-path errors.

Both are legitimate. Only (b) is general. Claims should say which.

**Classification: PARTIALLY IDENTIFIED.** The v3.8/v4.2 demonstration is genuinely (a). The generalisation to "the enterprise's own live systems of record" as a blanket property is **NOT IDENTIFIED**.

## K.5 What a properly identified design would need

To isolate *evidence independence* as a causal variable, arms must differ in evidence source and in nothing else:

| Arm | Evidence for the same claim | Everything else |
|---|---|---|
| **E1** agent prose only | `ProposedAction.claimed_*` | identical |
| **E2** retrieved context only | `retrieved_chunks` | identical |
| **E3** cached snapshot | a snapshot of the record taken at retrieval time | identical |
| **E4** fresh query | `registry/*.py` at decision time | identical |

Then `E4 − E3` isolates **freshness**; `E3 − E2` isolates **structure vs. prose**; `E2 − E1` isolates **retrieval**. This is exactly the ladder the brief calls A1–A5, and it is the right design. **None of it exists in the repository**, and it cannot be run until labels exist that the arms did not produce (`11`).

Note also: any such comparison must be scored on the **branch's** gold set with a **case-cluster bootstrap over `source_order_id`** (`docs/gold-set.md` §2: 50 ALLOW cases on 5 source orders), or the intervals will be wrong by a large factor.
